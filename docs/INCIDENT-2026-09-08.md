# Drill log, 2026-09-08

Four faults injected against the stack, three of which found a defect in the
alerting rather than in the pipeline. All four are recorded because the ones
that found nothing are the reason the ones that found something are credible.

## 1. Counters through a pushgateway report nothing

**Injected:** two successful runs, then queried `increase(pipeline_run_total[5m])`.

**Expected:** 2. **Observed:** 0, for every stage.

**Cause:** the job builds a fresh `CollectorRegistry` on every run, so a Counter
starts at zero each time, and `push_to_gateway` replaces the group rather than
adding to it. The series is therefore flat forever. `rate()` and `increase()`
both see no increase, because there is none.

**Fix:** the whole metric contract is Gauges with per-run semantics.
`pipeline_rows_processed{stage}` means "this run moved 400 rows", not "400 rows
have ever moved". Counters are for processes that stay up.

**Kept:** `pipeline_last_success_timestamp_seconds`. A pushgateway never expires
what it holds, so a stopped job leaves its last good push in place and any
dashboard built on run counts stays green through a total outage. A timestamp
goes stale on its own, and staleness is something a rule can match.

## 2. One fault, three pages

**Injected:** `PIPELINE_FAULT=transform_error`.

**Expected:** one page naming `transform`. **Observed:** pages for `transform`
and `publish`.

**Cause:** the run publishes a zero for every stage before starting, so that a
stage which never executes is distinguishable from one that is absent. That works,
but it makes "never ran" and "ran and raised" identical: both sit at
`pipeline_stage_success == 0`. Every stage behind the broken one pages.

**Fix:** a second gauge, `pipeline_stage_ran`, set on entry to each stage. The
rule became `pipeline_stage_success == 0 and on(stage) pipeline_stage_ran == 1`.
Stages that never got the chance are excluded.

## 3. The inhibit rules were backwards

**Injected:** the same transform fault, after fix 2.

**Expected:** a page saying `transform` failed. **Observed:** a page saying "no
successful run in 2 minutes", with the stage failure suppressed.

**Cause:** the inhibit rule read `PipelineStale` inhibits `PipelineStageFailed`.
That is the wrong direction. The stage failure is why there has been no
successful run. Inhibition has to run cause to symptom, and writing it backwards
is worse than having no rule at all, because it reliably delivers the vaguer of
the two alerts and swallows the specific one.

**Fix:** reversed, and the other two rules re-derived the same way. Verified by
reading `inhibitedBy` out of the Alertmanager API rather than by trusting the
config.

## 4. A config change applied cleanly and changed nothing

**Injected:** edited `alertmanager.yml`, ran `make up`.

**Expected:** Alertmanager restarted with the new rules. **Observed:**
`Apply complete! Resources: 0 added, 0 changed, 0 destroyed`, and the container
kept serving the old config. The fix from drill 3 was not live, and the apply
said everything was fine.

**Cause:** the config is a bind mount. Terraform tracks the container, not the
bytes inside a file the container happens to read at startup. Prometheus already
carried a `config.fingerprint` label for exactly this reason; Alertmanager and
the sink did not.

**Fix:** the fingerprint now hashes every mounted config, and every container
that mounts one carries the label, so a config edit forces a replacement. This
is the failure mode that matters most of the four: the other three were visibly
wrong, and this one reported success.

## What the drills prove

    01:52:17  resolved  PipelineStageFailed  Stage transform failed
    01:52:27  firing    PipelineDataStale    Newest ingested row is older than 1h

A page fires, names the stage, suppresses the cascade, resolves when the fault is
removed, and a separate alert notices that the data went stale while the runs
were still succeeding.

## 5. "Since last successful run: 56.7 years"

**Injected:** a healthy run, then a failed one. Looked at the dashboard.

**Expected:** roughly a minute. **Observed:** 56.7 years, which is the Unix epoch
subtracted from now.

**Cause:** a push replaces the entire group. The failed run pushed a
`pipeline_last_success_timestamp_seconds` that had never been set, so it went out
as its default of zero and erased the real timestamp from the successful run
before it.

**Fix:** two registries under two grouping keys. Per-run metrics go to
`part="run"` and are replaced every time, which is what they are for. The
liveness timestamp goes to `part="liveness"` and is only ever written by a run
that finished every stage, so a failure cannot erase it.

**Also learned:** changing a grouping key orphans the old group, and a
pushgateway keeps orphans indefinitely. The stale series survived the change and
had to be deleted with `DELETE /metrics/job/nightly`. Without
`--web.enable-admin-api` there is no wipe, only per-group deletes.
